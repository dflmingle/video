# 制作与技术方案的详细规则

目标是让用户核实“准备做什么、依据是什么、怎样实现、如何验收”，而不是提前给工程贴完成标签。小项目可一份文档，复杂项目可拆主方案、参考审计及需求对应表并互相链接；不强制页数、文件名或汇报格式。

## 1. 恢复来源与确认范围

按原章节检查正文、跨页表格、图片/图注、附件、链接、用户补充及历史确认。文字提取不清楚的页实际渲染查看；表格中的图、链接与角色行对应，不能错配到相邻兵种。已有指定资产应列明，不能整表写待确认。

工作顺序：恢复需求与现状 → 逐项拆解 → 按用途核对参考 → 制作与技术方案 → 查漏与审阅 → 按有效授权制作。

核实前允许只读调查、参考解析与文档整理；需要实现实验才能判断的事项写清验证任务和标准，按已授权范围处理。先完成可审阅文档再请求必要核实，不问“要不要写方案”。收到“已收到”不等于确认，但明确继续制作、按已确认方案修复或同步更新方案并实施的授权无需重复申请。更新记录指向具体版本、范围与条件。

## 2. 建立稳定的需求对应表

每个独立要求给稳定 ID，可合并同义项，不可概括掉小效果或强制状态。

| 字段 | 必须写清 |
| --- | --- |
| 来源与要求 | 文档页/节/图或用户消息；谁在何时对谁做什么，期望什么结果 |
| 约束等级 | 必做结果、允许窗口、可调参数、参考做法、工作假设、真正待决项 |
| 可见与有效状态 | 观众看到什么；实际需要生效的输入、移动、占位、攻击、加成或禁用状态 |
| 实现 | 模块、数据、素材、触发条件与依赖；最终状态由谁写入 |
| 验收与失败 | 哪段连续画面、哪个对象/状态；什么现象直接算失败 |
| 当前进度 | 已核对、方案覆盖、待验证、已实现、当前版本已检查分别标记 |

“数值/具体操作仅供参考”允许替换算法与参数，不取消对应效果。例如“禁用反击”不能变成降低攻击频率，“全军增益”不能悄悄变成小范围粒子。后续纠正只替代明确冲突的旧要求。

## 3. 按用途逐个核对参考

参考清单记录来源、所在需求章节、用途、指定时间段、取得状态及实际查看范围。区分完整剧情出处、主片节奏、个体移动、阵型切换、特效、界面与角色资料；看完主片不能代替各节独立视频。

- 时间点看前后，覆盖动作进入、持续、退出与转场。动态细节看连续帧，关键区域放大；截图带源时间与帧号映射。
- 用户要求逐帧时，对约定范围逐帧目视覆盖；只解码/导出所有帧不算看完。常规分析按动作速度选择样本，不强制全长逐帧。
- 写“可见事实 → 本次采纳的特征 → 实现与验收决定 → 无法确认的部分”。不要只贴图或复述标题。
- 分清部署预览与实际队形、命令箭头与弹道、选择描边与闪白、相机运动与主体移动、遮挡与穿行。画面不能单独证明内部算法或真实数值。
- 原片观察、用户要求效果、制作决定分列。原片没做某项效果不取消用户新增要求，新增效果也不伪称原片事实。称“需求要求效果”，不要以 PDF 等文件格式命名效果。
- 不可访问、未下载、未看或未听均如实标记；替代来源未经比对不称同一文件。必要时保留规格、源标识或哈希，避免错误副本。

## 4. 先梳理因果，再写时间表

先用文字或流程图还原双方目标、初始部署、决策、行动、触发、反应、转折、结局，明确局部胜负与全局结果。战斗示例中的“分兵包围 → 中央空隙 → 敌方突破”是因果关系的写法，不是所有项目固定剧情。

每段列：顺序/时间窗口 → 主体与动作 → 观众应理解的变化 → 素材/空间/UI → 不可变职责和结果 → 下一阶段条件 → 直接证据。

- 参考时间、需求时间、拟制作时间分别标记；需灰盒验证的卡点不冒充已经核实。
- 包围交代翼侧从哪来、封住什么、何时收拢；突破交代哪方受压、开口如何产生、谁通过及穿过后怎么改变局势。仅数方位或播放字幕不成立。
- 时间冲突先查路程、速度、转向、容量及事件依赖；不为赶时间跳位、远处杀人、删掉阶段或改伤亡归属。
- 用平面草图核对地形、通道、接战区、镜头范围、纵深与 UI。复杂群体的灰盒必须有代表性的密度，少量小球不能验证兵潮和拥堵。

## 5. 方案完整内容

| 部分 | 需要写到可执行、可评审的程度 |
| --- | --- |
| 目标与交付 | 可玩/演示/视频，用户输入和规则，已知时长/画幅/帧率/音频，当前阶段和工作假设 |
| 依据与替换 | 保留原片、自研素材替换、需求新增效果、未知项分别列；说明实际核对范围 |
| 剧情与空间 | 全流程因果、分镜、路径、可行区、通道容量、相机、留白和画外持续对象 |
| 机制与效果 | 每项的触发 → 有效对象/范围 → 状态改变 → 视觉组成/先后 → 持续/退出 → 模块 → 失败条件 |
| 资产与数量 | 原职责 → 指定素材 → 格式/动画/武器/音效 → Web 产物 → 缺项；编队、成员、模拟个体、渲染数量分别列 |
| Web 技术方案 | 现有环境、选型及理由，2D/2.5D/3D，资产转换，模拟/渲染/时间权威，输入、音频、启动/构建、录制及缓存失效方式 |
| 推进与风险 | 依赖顺序、各阶段产物和退出条件；风险对应先做的验证、失败替代和受影响要求 |
| 验收与确认 | 逐项直接证据，版本与限制，浏览器实测、连续画面、编码导出、待决项与确认范围 |

技术选型不能只列引擎名称。写清为什么满足素材、镜头、人数和交互；区别真实三维、烘焙方向精灵和预编译演出，说明其视角与输入限制。源资产没核实前不给虚假精确的性能或工期承诺。

## 6. 文档自身也要验收

对照原章节与逐项表查漏，特别检查方案细化、已有素材、独立参考、强制状态及各段因果。主方案、详细表与技术方案的职责、数量和结果一致。

区分需求、观察、建议、假设、已实现与已验收。Markdown 检查链接和表格；若交付 PDF/DOCX，实际渲染查看全页，放大新增/复杂页检查中文、跨页表格、图注、比例与溢出。生成成功不等于版式通过。

记录源文档与导出版本，提供最新入口、变更及待决范围。方案通过不等于实现完成；项目具体时间点、路径、素材及截图留项目文档。
