# V22 透视镜头与交战时间求解

## 范围与真实基线

本分支只新增 `src/camera-v22.js`、`tools/timeline_v22.py` 和本说明，不修改运动、射手、箭矢、人数、初始坐标或渲染入口。父任务负责集成和正式渲染。

实际读取 `variants/V21/simulation.json`、`trajectories.npy` 和 `blue-control.npy`，非凭旧报告推断。252 蓝方、972 红方，60 Hz，红方速度 21.75，射程 34，箭速 72，武器包络半径 3.1，最低表面间距 4。

`tools/capture_v20.mjs` 默认传 `camera=FIXED`；`src/camera-v19.js:createBattleCamera()` 的 presets 仅有 A/B/C/D，未知值回退 A。因此 V21 实际末段 zoom 是 **2.05**，不是先前可能误认的 B/2.5625。实际 `main-camera.js` 创建的是 `THREE.PerspectiveCamera`，不是正交相机。

初始红方 x=[-10.383,10.331]、z=[-102.384,-42.959]；蓝方 x=[-19.35,19.35]、z=[21.65,41.35]。逐点透视投影确认旧 openingZ=-20、openingZoom=1.35 已完整容纳三军和 U，故不为“修构图”无谓修改第一帧。

## 可接入镜头

API 保持 `createBattleCamera(S,C,positions)`；父任务把 import 指到新文件即可。URL 明确使用 `camera=A` 或 `camera=B`；`FIXED` 明确别名到 A，其他未知值报错，防止再次静默误用。

| 参数 | A：实际 V21 基线 | B：人物像素增大 |
|---|---:|---:|
| opening zoom | 1.35 | 1.35 |
| combat zoom | 2.05 | 2.5625 |
| opening/combat center Z | -20 / -4 | -20 / -4 |
| 推近起点 | redChargeStart + 0.72 | 绝对时间 0.72 |
| 推近终点 | duration - 0.16 | duration - 0.16 |

无 hold 时 A 与 V21 曲线相同；新时间线可通过 `C.redChargeStart`（兼容 `redChargeStartTime`）传入红方起跑延迟。B 使用蓝方可见部署阶段摊薄相同 16 世界单位的中心平移，不从实时全军包围盒拟合，不追加跟踪红方中心。A/B 的末段 pose、FOV 相同，B 因 zoom 增大而获得严格 25% 像素增幅，非世界模型缩放。

相机目标、zoom 使用连续 quintic 曲线，端点速度/加速度均为零；`motionBounds` 返回曲线的解析最大速度/加速度，不能把它误认为无限制的跟随系统。hold=0.8 时，A 中心峰速 20.882，B 降为 13.413 世界单位/秒，B zoom 峰速 1.016/秒。B 峰速仍非零，正式片需检查是否抵消推进；本模块不宣称已经完成视觉验收。

`fronts` 是黄色前沿 24 人的均值；`defenses` 是最近的 72 名蓝射手区域均值；`desired` 记录两者 0.6/0.4 的联合重心，用于诊断。它们**不反馈驱动镜头**，避免因伤亡或排序变化引入构图跳动。空间轨迹保持已验证旧构图，仅调整尺度和推近时间分配。

## 透视像素与可见率

投影按实际透视相机位置 [0,240,95]、目标 [0,0,-5]、FOV42、1440×2160 编码尺寸计算，并用 Three.js `Vector3.project()` 独立核对。人体高度探针为地面到 1.5 世界单位，是几何投影高度，**不是模型完整轮廓或动作可读性的主观证明**。

| 时刻（hold=0.8） | A 黄兵高度 | B 黄兵高度 | A 蓝射手高度 | B 蓝射手高度 |
|---|---:|---:|---:|---:|
| 开场 0 | 10.04 px | 10.04 px | 4.77 px | 4.77 px |
| 中段 1.567 | 9.47 px | 12.15 px | 5.23 px | 7.00 px |
| 旧命中对应时刻 2.683 | 13.43 px | 17.02 px | 9.75 px | 12.39 px |
| 结束 3.117 | 13.03 px | 16.28 px | 10.01 px | 12.51 px |

B 在逐帧“延迟红方、蓝方按绝对时间部署”的轨迹探针中，黄兵与蓝方中心投影的最低可见率都为 100%；开场三军和蓝方全部中心入镜。后段红后军会自然裁出，属于有意取舍。此检查未包含武器边缘、原生动画完整包围盒或场景遮挡，需正式渲染补验。

## 真实时序与约束

原片控制数据的实际首批准备完成不是 units 元数据中的 readyAt≈1.11，而是控制状态首个 AIMING 在 **1.333 秒**。实际首放箭 1.583、首命中 1.883、安全末帧 2.317，首命中后仅 **0.433 秒**。

求解器逐点插值红方 `baseline(max(0,t-hold))`，蓝方用绝对时间 baseline(t)，录制结束后蓝方保持已到达位置。结束时机按 KD-tree 最近双方中心距离，减去双边武器包络，再减半步最大位移的保守连续运动余量计算，未把 center gap 冒充 surface gap。

释放时必须满足射程。箭矢飞行通过目标**未来轨迹逐点求交**进行二分求根，非直接用释放距离/箭速。命中绑定候选具体目标。以下均为单次首击可行性上界，非新的完整射击调度，不包含目标争抢、受伤后重新模拟和精确 native hand 发射点。

| 起跑 hold | 安全结束 | 入射程后才 aim+draw：首击 / 窗口 | 可提前 aim、入射程才 draw：首击 / 窗口 | 预拉弓上界：首击 / 窗口 |
|---:|---:|---:|---:|---:|
| 0 | 2.317 | 1.861 / 0.455 | 1.861 / 0.455 | 1.861 / 0.455 |
| 0.8 | 3.117 | 2.549 / 0.567 | 2.486 / 0.631 | 2.357 / 0.760 |
| 1.0 | 3.317 | 2.749 / 0.567 | 2.686 / 0.631 | 2.557 / 0.760 |
| 1.2 | 3.517 | 2.949 / 0.567 | 2.886 / 0.631 | 2.757 / 0.760 |

hold=0.8 时首个射程进入绝对时间 2.0，相对起跑 1.2。严格流程选中的首个有效发射 2.25、射距 28.491，飞行 0.299 秒。提前瞄准方案释放 2.167、射距 30.272、飞行 0.319。预拉弓上界释放 2.0、射距 33.765、飞行 0.357，仍仅 0.760 秒。

**结论：仅延迟起跑和提前瞄准不能提供 1 秒命中后窗口。** 它们能增加部署可见时长，并缓解射手尚未到位的时间损失；不能扩大“射程 34 到最低安全边界”这一有限空间。hold 从 0.8 增到 1.2 只平移事件，不进一步延长箭雨窗口。若要求 ≥1 秒，至少需另行放宽射程、箭速、冲锋速度、安全边界或场景空间中的某个条件。此分支没有擅自应用任何一项。

`preDrawBound` 是“可在有效释放射程外预拉弓、入射程才放”的**未应用乐观假设**；它不满足严格的先射程有效再进入 DRAWING 的策略，父任务须明确决定策略后才可使用。`firstFramePreparedNotApplied` 是改变首帧准备状态的理论对照，同样未应用；它在 hold=0 时也仅 0.745 秒。没有隐藏负时间准备或超射程命中。

## 可重复检查

运行：

```powershell
python tools/timeline_v22.py --variant variants/V21 --holds 0 0.8 1.0 1.2
python -m py_compile tools/timeline_v22.py
node --check src/camera-v22.js
```

结果写入 `output/V22-timeline-prospective.json`。自动检查开场三军可见、黄前锋/蓝发射区域逐帧中心可见、末段像素增加恰为 25%、保守安全间距、实际释放射距。失败以非零退出，不仅输出日志。此次六项数值检查全部通过，Python/JS 语法检查通过；Three.js 投影和连续单调 schedule 独立探针通过。

**未完成：** 本隔离任务没有接入生产入口、没有重算战斗、没有渲染 MP4、没有正常速度观看。近景动作、遮挡、镜头推近观感、箭矢释放动画对齐和最终安全距离必须由集成后的实际产物再次验收。不能用这些前瞻计算代替正式视频证据。
