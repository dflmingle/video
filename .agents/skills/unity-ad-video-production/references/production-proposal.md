# 需求拆解与制作方案文档

用于新投放视频及涉及剧情、资产职责或表现机制的实质改版。目标是先让用户核实“准备做什么、参考了什么、怎样实现、怎样验收”，再进入制作。本文是跨项目方法；具体剧情、人数、秒数、资源链接和截图留在项目记录，不固化为Skill默认参数。

## 1. 工作顺序与制作边界

需求/历史恢复 → 全量需求拆解 → 按用途核对参考 → 形成制作方案及逐项对应表 → 检查文档 → 提交具体版本供用户核实 → 按确认范围制作。

- 核实前可读取工程环境、检查已有资产、下载参考、分析连续帧、验证文档排版和整理技术可行性；不创建或修改制作场景、Unity运行时脚本、正式演出资产，不启动录制。需要工程实验才能确定的事项先写为验证任务及判定标准。
- 不用“要不要我写方案”阻塞已授权的文档工作。先把可审阅的方案做完整，再请求核实。缺项不影响方案时，写明工作假设与影响，继续独立工作。
- 用户确认后记录版本、确认内容、条件及遗留项。“已收到”“文件生成”和助手自行检查不等于用户确认。用户明确指示继续制作或已提供有效授权时按上下文执行，不机械重复确认。
- 实施时保持方案与现状一致；仅局部修复就在原确认范围内推进。涉及剧情结果、职责或新增范围的变更更新对应条目，必要的核实只针对该变更。

## 2. 全量拆解需求，不能只读文字摘要

按原文节次检查正文、跨页表格、图片、图注、链接、附件、用户后续纠正和历史确认。尤其检查“方案细化、机制/替换、视觉落地”等章节，不能仅抽取开头大纲。文字提取不能还原的表格，要渲染并放大查看；不能把跨行图片/链接误分给相邻兵种。

每个独立要求建稳定ID和来源定位，可合并重复项，但不得遗漏或弱化：

| 字段 | 应写清的内容 |
| --- | --- |
| 来源与要求 | 原文页/节/图/用户消息，谁在什么阶段做什么，要求什么结果 |
| 强制程度 | 已确认必做、允许窗口、可调参数、参考做法、工作假设或待核实项 |
| 表现与有效状态 | 观众能看到的变化，以及应实际生效的移动、攻击、士气、容量等状态 |
| 实现落点 | 数据、模块、事件、资源与依赖，谁负责输出最终位置/状态 |
| 直接验收 | 看哪段连续画面、查谁的状态、什么现象算失败 |
| 当前状态 | 已核对、方案已覆盖、待验证、已实现、当前版本已验收分别记录 |

“数值和具体操作仅供参考”允许替换算法、API与数值，不允许删除对应效果。区分不能变的结果与可调方法。例如“失去反击判定”不能改为攻击减少；“全军加成”不能未说明变为附近范围；阵型不能只换外形却没有规定的战斗差异。

后续纠正只替代明确冲突的旧要求；原片没有某项效果，也不取消用户明确要求的新增效果。用“需求要求效果”称呼目标效果，PDF等仅作为来源格式，不写成“PDF效果”。

## 3. 每个参考都按其用途仔细核对

先列参考清单：链接/文件、需求中所在位置、用途、指定时间点、取得状态。区分主片节奏参考、完整剧情出处、个体运动参考、特效/动画参考、资产/机制资料；主片看完不能代替各节独立效果视频的查看。

- 时间点链接要看动作前后，覆盖进入、持续、退出和状态切换。用连续帧或视频核对动态；复杂细节放大主体，保留时间戳及证据路径。
- 用户要求逐帧时，对约定范围逐帧目视覆盖，并对细节补充放大；仅生成抽帧文件不算已看。常规分析按动作速度选连续采样范围，不一律全长逐帧。
- 记录实际核对范围：全片逐帧、指定段连续观察、间隔定位抽查、音轨听验分别说明。未看/未听、需登录或下载失败的来源如实标记；有可用替代可继续工作，但未经比对不能宣称不同文件相同。
- 保存必要的源标识、规格、版本/日期及关键证据；可能混淆副本时记录哈希。帧号、截取段局部时间和源视频时间必须能对应。解码/定位异常先修复，再重新生成受影响证据。
- 区分实际动作与部署预览/目标轮廓，命令线与弹道，选择描边与受创闪白，相机运动与主体运动，遮挡与通行。可见变化不能直接证明内部算法、真实米数速度、伤亡人数或数值加成。

观察记录至少写：来源与时间段 → 可见事实 → 本片采纳的特征 → 实现/验收决定 → 无法确认的部分。不要只贴截图或复述视频标题。

## 4. 制作方案应包含的内容

按复杂度组织，简单任务可一份短文档，复杂项目拆主方案、参考审计和详细对应表并互相链接。领导版便于评审，详细版便于实施；两者内容一致，不强制固定页数或文件名。

### 目标、边界与依据

说明用途、核心表达、时长/画幅/帧率/音频/交付物的已知值与假设，当前是方案、预览还是成片阶段。列需求与参考来源、已核范围、资产取得/验收状态。引用历史材料时注明版本背景。

### 原片与本次要求的关系

明确列出“原片保留 / 自研替换 / 需求要求效果 / 待核实与限制”。原片事实、需求解释和实现建议分列。保留节奏或战术骨架不等于只能复刻原片已有表现；新增效果不能被伪称为原片事实。

### 分镜与剧情契约

时间窗口或先后顺序 → 主体和动作 → 观众应理解的变化 → 角色/道具/UI → 不可变结果 → 与上下游衔接 → 验收镜头。说清伏笔、转折、高潮、结尾的因果，范围适用时区分局部胜利与全局结局、画内与画外持续对象。

需求时间、原片可见时间及拟制作时间不一致时分别注明；确切帧需灰盒验证的写明，不编造已核卡点。不能为了局部动作删阶段、改职责、改变命中归属或临时清空无关角色。

### 机制、动作和效果逐项落地

对每项要求写“触发条件 → 有效对象/范围 → 状态改变 → 视觉组成与先后 → 持续/退出 → 实现模块 → 验收/失败条件”。不能把排枪、后坐复位、烟雾、闪白、混乱和禁用反击笼统归为“战斗反馈”。

运动需求区分整体路线、局部位移/避让、动画/姿态；行走、转向、受击退却、停止和恢复分别覆盖。阵型要求区分槽位形态、过渡、实际成阵及其火力/机动/防御差异。参考数值标为初值，说明怎样随尺度和画面校准。

若涉及群体空间约束，沿用Skill的空间参考：ORCA加实际接触保护；桥Mesh/MeshCollider与运动边界同源。写清实际数据连接，不能列组件名称冒充实现。非相关镜头不引入这套系统。

### 资产与数量对应

原兵种/道具职责 → 已指定的自研图片/链接/资源 → 动画/武器/音效需求 → 本片用途 → 能力疑点/缺项。先查看原表，已有指定不能整表写待确认；有图片/链接不能称资源已下载或动画齐全。武器外观与任务职责冲突时列出适配任务，不能悄悄删攻击方式。

分清战术单位、编队、渲染个体、炮型标签和部署数量，不把表格合计自动当单兵数或重复乘算。保持分组和稳定身份，需要画外返回时不删除重生。

### 技术、推进顺序与风险

写清实际环境、可复用部分、独立目录/场景边界、权威数据流与时间求值。说明Unity运行/录制、Timeline编排、Codex协作实施、Skill流程规范各自职责；无须为简单片强制使用每种工具。不能将Skill说成运行插件，也不能把确定性演出宣称完整自主AI。

按依赖列阶段产物与退出条件：资产/空间 → 剧情灰盒与难点小样 → 正式资产和表现 → 全片精修 → 录制交付，可按项目调整。每个风险关联先做什么验证、失败怎么办、影响哪些结果；资源未核时不给虚假精确工期/性能承诺。

### 验收、待决项与确认范围

需求每项能追溯到具体镜头或状态检查；截图看布局/轮廓，连续片段看动态过程，必要状态记录证明实际判定。指标要能抓住原问题，不能只数事件、组件或总人数。

说明编译/导入、当前版本证据、重播/跳转需求、实际导出检查及交付边界。列清已知限制和会影响实施的未决项，提出有依据的工作假设。最终用户核实的是具体版本和范围；文档覆盖完整不代表工程实现完成。

## 5. 文档交付前检查

1. 对照需求原节次与逐项表查漏，特别检查图表中的已有资产、独立效果视频、强制状态和容易概括掉的小效果。主方案、详细表、汇报版与摘要不能互相矛盾。
2. 确认措辞区分“需求要求、原片观察、建议、待核实、已实现/已验收”；没有原片依据的效果不伪装为观察结果，访问失败不记为已看。
3. Markdown检查表格/链接可读；DOCX/PDF等成稿实际渲染查看全页排版，并放大新增/复杂页，检查中文、表格分页、图注、图片比例、页眉页脚、空白/溢出。文件生成成功不能代替看图。
4. 源文档、生成脚本和导出同步，核对版本和时间戳。文件被占用时另存清晰的新版本，不覆盖用户正在编辑的内容；标明最新入口，避免误读历史稿。
5. 交付精简说明改变、证据与实际限制，给主要文档及详细依据链接。保存项目状态和待确认范围，使后续无需重读整段聊天；未获制作确认时不提前开始Unity实施。
