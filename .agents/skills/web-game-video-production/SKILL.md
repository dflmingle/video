# Web 游戏演示与视频制作

把需求要求效果落实为浏览器里能运行、能核对、能交付的作品。保留 Unity 视频制作流程的需求与验收约束，技术选型按 Web 项目重新判断，不要求运行 Unity。

## 1. 先恢复需求与现状

- 阅读用户原话、原始文档、图表、附件、各节独立参考、已确认方案与后续纠正。尤其细读“方案细化、关卡流程与剧本设计、角色替换、机制效果”等实质章节，不能用文档摘要或主视频替代。
- 先确认交付形态：可玩 Web 游戏、可控脚本演示、录制视频，或组合。用户要游戏时必须落实约定的输入、规则与反馈；用户只要演出时不擅自扩成完整游戏。固定演出不称完整自主战斗 AI。
- 有现有项目就恢复最新代码、启动方式、有效验证及限制；历史报告带版本背景。分支实验与主项目的目录、进程、端口、输出明确分开，不能因为改用 Web 而改坏原工程。
- 实现问题先锁定对象、阶段、可见现象及期望结果，再找根因。同一问题反复被指出时读 [返工案例](references/rework-cases.md)，重审对象、模型与证据，不只叠加特效或补丁。

## 2. 先出可审阅方案，再按授权制作

新项目及涉及剧情、资产职责、交互规则或表现机制的实质改版，先读 [制作方案规则](references/production-proposal.md)。完整拆解需求，核对参考，提交有具体版本的制作与技术方案供核实。

- 核实前可阅读环境与素材、分析参考、评估可行性、完善文档；不提前展开尚未授权的正式制作。已有确认与当前授权持续有效，用户已明确“按方案制作”“同步改方案并重做”时完成文档更新后继续，不机械重复请求确认。
- 确认范围内的局部修复直接推进。只有真正缺失且会改变方案的信息才澄清；不影响推进的假设写清依据与影响。
- 方案必须覆盖“来源要求 → 剧情/交互因果 → 空间与时间 → 素材对应 → 技术数据流 → 直接验收”。方案里写了不等于代码已经实现。
- 参考观察、需求要求效果、制作决定、工作假设分别记录。允许调整参考参数不等于允许删掉要求的效果；用户纠正仅替代明确冲突的旧要求。

## 3. 先打通完整流程，再精修表现

实施前按需要读 [Web 实现规则](references/web-implementation.md)。选择适合镜头与交互的技术，优先复用现有工程；不默认固定引擎、渲染方式或庞大的开发框架。

涉及参考中已有的重要视觉事件且使用 Web/Three.js 渲染时，读 [特效实现与编码可见性](references/effects-rendering.md)，核对坐标/挂点、连续轨迹、生命周期、屏幕尺度和最终合成。仅实现参考支持或明确授权的阶段，不为普通视频强加炮击、爆炸或粒子。

1. 核实原素材、动画、坐标/尺度与浏览器可用方式；缺素材和已取得素材分清。若需将模型烘焙成多方向精灵，先说明质量、视角与动画限制。
2. 用能代表目标密度与空间规模的灰盒，贯通完整剧情和关键交互。核对每次转折的触发、职责、路径、结果及下一阶段，不用结尾字幕代替过程发生。
3. 建立位置、状态与时间的权威来源，再加正式素材、动作、特效、UI与音效。不能让脚本、局部避让、缓存和渲染各自覆盖最终位置。
4. 用实际目标画幅迭代构图、密度、节奏与可读性。复杂人群按真实占位与可行区域约束，不通过远处停步、穿模、瞬移或删除角色凑战果。
5. 浏览器中启动当前版本，完成所需交互、重播/跳转及录制验证，再交付工程入口或成片。

战斗或群体演示必须先画清双方目标、兵种职责、分组、进出路径和局部/全局结果。“包围”要有实际封堵与收拢，“突破”要有受压、开口与穿过后的变化；不能用人数、箭头和文字宣称已经发生。

## 4. 素材、数量与行为必须对应

- 沿用用户指定素材，记录原文件到 Web 产物的映射。临时几何、占位模型和新增视觉素材标明用途，不能用无关圆点代替已有正式角色后声称完成替换。
- 分清战术单位、编队、每队成员、实际模拟个体与渲染实例。需求中的“单位”含义先从上下文核实；既不能把一个编队当一名士兵，也不能未经依据重复乘算人数。
- 画面需要密集军队时，阵列纵深、局部间距、持续补入、通道容量、镜头尺度一起验证。装饰副本不能冒充有独立占位、移动、受击与死亡的士兵。
- 实际能力由角色职责和状态定义，不根据模型尺寸、贴图方向或碰撞半径猜测兵种。缩放美术时不得悄悄改变攻击能力与战斗结果。
- 反馈反映真实因果：攻击有有效目标，命中与受击对象一致，死亡及特效不牵连旁观者。保持稳定身份，死亡不重排活人；画外回援需要持续状态。

## 5. 自己看浏览器与导出，不把验收留给用户

按 [浏览器验收与录制规则](references/verification-recording.md) 留证。

- 修改视觉或动态前保存基线；确认新代码和资源实际加载，在目标浏览器、画幅与相机下查看截图。连续帧/录像覆盖进入、持续、退出及状态切换。
- 每个检查问：“原问题仍存在，这个检查能否仍然通过？”能通过就补直接证据。不能用总人数、事件次数、无控制台报错代替指定对象在指定阶段正常。
- 核实素材、模拟缓存、前端构建、音频与导出来自当前版本。改输入后重新生成受影响缓存；旧 PASS 和旧视频不能验证新代码。
- 录制按确定的时间基准同步模拟、渲染、动画、粒子、UI及声音。检查实际编码视频，不能只看浏览器预览或封面。
- 重要视觉事件按参考适用阶段逐事件核对最终 MP4 的起始、传播、结束与残留，覆盖全片及后半段；发生时间、位置、方向、尺度、亮度和持续须有证据。代码调用、事件数量、实例数及预览不能单独判 PASS，参考不可见阶段记未知或不适用，不补造。
- 如实记录核对范围：全片播放、指定片段连续查看、抽帧或逐帧分别说明。生成了所有帧不等于逐帧看完，有音轨不等于已经听验。
- 修复已发现的明显问题再停；验证范围与修改风险相称，已有检查通过后无新修改、失败或疑点就不重复扩大测试。

## 6. 交付与经验沉淀

给出可用启动命令、实际访问地址、交互说明、主要文档及输出路径；用户要求启动就实际启动并检查页面可访问，不只告诉用户命令。已存在服务先核对归属与版本，不随意终止其他项目进程。

报告具体改变、当前证据及实际限制，区分工程检查、助手视觉验收和用户认可。说明交付是否可玩、是否使用原始三维模型或烘焙精灵、是否依赖预编译模拟、是否只是脚本战斗及适用视角；无需列无关假设风险。

通用失误与有效方法写可复用参考；剧情、人数、时间点、链接、端口、素材路径、截图和确认记录留项目文档，不写成 Skill 的固定参数。没有用户最终认可的结果不能记成最终成功。
