# Web 实现与运行规则

只对当前任务需要的部分应用；不把群体战斗、完整回放、离线缓存或复杂引擎变成所有项目的必需项。

## 技术选择与工程隔离

先读现有入口、依赖、构建/启动脚本、资源和部署方式。能复用就复用，缺能力才引入依赖。新建实验按用户要求放独立目录，明确端口与输出，避免写入原 Unity 工程或终止无关进程。

| 场景 | 可考虑的方式 | 需要先验证 |
| --- | --- | --- |
| 简单 2D 或界面演出 | Canvas、现有 DOM/CSS 或已有渲染层 | 目标分辨率、叠层、字体、动作与录制一致性 |
| 大量 2D 角色与动画 | PixiJS、Phaser 或现有批绘系统 | 图集、透明边缘、排序、实例量与内存 |
| 真实 3D 镜头与模型动画 | Three.js、Babylon.js 或现有 WebGL/WebGPU 项目 | 骨骼、材质、阴影、动画、实例化与目标设备 |
| 固定相机、大规模原模型展示 | 经确认后烘焙方向精灵、混合渲染或模型实例化 | 视角/光照限制、转向跳变、近景质量、遮挡与资源体积 |

选型按项目，不必逐个安装尝试。Web 技术不等于 Unity WebGL 导出；用户要求脱离 Unity 时，运行与构建不应暗中依赖 Unity。需要源包提取或转换工具时，如实说明处理阶段依赖，不更改源工程。

## 原素材落地

建立清单：源文件 → 角色/道具职责 → 材质/纹理 → 动画片段 → 转换方式 → 浏览器产物 → 限制。实际检查包内容，不能把 `.unitypackage` 文件存在当作模型、动画已可用。

- 保留原素材副本与可重建的转换参数，不覆盖源文件。模型单位、轴向、枢轴、贴地基准、武器挂点、透明贴图和颜色空间一起核对。
- 使用原始模型时检查骨骼动作、根运动与路径是否重复位移；烘焙精灵时记录方向、帧序、动作时长、锚点、像素密度、阴影处理及适用相机。
- 烘焙结果逐动作、逐方向抽查透明边缘、裁切、闪动、大小与武器。跑步、攻击、受击、死亡不得共享错误帧序；朝向是角色世界方向相对相机计算的结果。
- 用户要求原素材时，占位可用于已授权灰盒；正式交付仍需替换和核对。不能把外观替换当作职责已实现，也不能默默改成无关素材。

## 数据、时间与输入

需要实现可重复的视觉事件/特效时，读 [特效实现与编码可见性](effects-rendering.md)；仅包含已运行验证的坐标、分层与绝对时间方法，不提供通用物理/粒子引擎。

分开模拟状态与渲染状态。明确固定步进或项目现有时间模型，保持统一输出时间；路径、骨骼/精灵动画、粒子、UI、音效不能各用互不相关的墙钟。

- 最终位置、朝向和生存状态各有明确写入者。全局路径给意图，局部运动约束给合法位移，再由渲染读取；不要在渲染循环改权威战斗状态。
- 按职责区分剧情编排、真实规则与局部自主行为。镜头要求的关键事件可编排；不能声称脚本时间表就是完整 AI。
- 可玩模式验证真实输入 → 合法指令 → 状态变化 → 画面反馈 → 胜负/循环。预计算且无法响应输入的演出，不冒充玩家实时控制；混合模式说明输入如何影响后续状态。
- 暂停、重播、跳转或回退只在要求范围内实现；涉及随机则固定种子或保存状态。顺播与目标时刻重建须一致，粒子、死亡、音频、UI与结束锁存也要处理。
- 后台标签页节流、窗口缩放、不同像素比与失焦恢复按使用场景验证。音频遵循浏览器实际用户手势策略；自动播放被阻止时给必要交互，不编造已播放。

## 群体与空间：需要时才启用

先明确编队、模拟个体、渲染实例及其关系。装饰性成员可用于允许的镜头，但不能用来宣称独立碰撞、受击或战术行为；需求要求真实个体时，每个活成员有稳定身份及实际状态。

- 地形显示、导航/通道和碰撞边界使用同源几何或明确可核对的映射。桥口、曲线岸边、拐角和窄道检查真实轮廓，不用粗略矩形/分区代替可行区。
- 先规划整体路线与汇入，再处理占位、局部避让和接触保护。按实际密度与性能预算选择合适算法；不能只添加碰撞组件，或强制所有项目使用某一种算法。
- 碰撞覆盖需求涉及的同阵营、异阵营及静态障碍。局部推挤后重新验证边界和接触；一方被拒绝移动时，下游占位不能继续按原移动假设结算。
- 曲线路程按世界空间累计距离处理。队首与后列分开检查，避免少数前排高速冲锋、后方缓慢或全员同步停顿；必要时分战术小组，不用单个编队中心拖动整队替代个体转向。
- 阵型槽位是目标，不是瞬移指令。换位逐人走路径、转向、避让再整队；死亡不重排存活成员，回援保持原身份与状态。
- 接敌、攻击、命中、伤亡与特效共享有效目标和事件来源。角色能力显式定义，不能由碰撞半径阈值或美术比例推断。
- 密度同时检查局部间距、纵深、通道容量、持续补入和镜头尺度。合围必须实际形成战术压力，突破必须有通过空隙的连续动作，不能只看区域计数。

## 缓存、加载与性能

若确需预编译模拟、动画图集或缓存，记录所有影响产物的输入及版本：模拟代码、配置、几何、素材转换、种子、时间步长等。使用内容哈希或可靠依赖检查；代码更新后旧缓存必须失效。缓存状态与浏览器绘制依然是不同验证对象。

- 先测实际瓶颈，再用图集/批绘/实例化、空间索引、适当精度、压缩或分段加载；不能以删掉剧情或把碰撞换成装饰复制来优化。
- 下载体积、解压内存、解析时长、首屏时间和帧耗分别观察。开发机本地流畅不等于远程加载已优化。
- 检查服务器实际响应头、类型与响应体。浏览器可能已按 `Content-Encoding` 解压，不能只看 `.gz` 后缀再次解压；开发/预览/正式服务均核对受影响路径。
- 处理资源路径、大小写、CORS、纹理加载、字体与音频完成信号。录制等所有必需资源就绪，不能用固定延迟掩盖加载竞态。
- 启动后确认实际入口、端口、当前构建与浏览器控制台。浏览器打不开或启动被拒绝时如实记录，通过允许方式提供入口，不绕过工具拒绝。

技术方案写出的数据流应在代码与产物中真实成立。若改模型或选择替代技术影响已确认镜头、可玩性或质量，更新对应方案并说明具体影响。
