# Unity 投放视频制作

交付目标是符合用户脚本、表达清楚且可稳定录制的视频。实现复杂度服务于镜头需要，不默认建设完整游戏，也不预设战斗、双路对抗、特定人数或导航算法。

## 1. 先拆解需求、出制作方案，核实后再制作

**新视频或实质改变剧情、资产职责、表现机制的制作任务，先完成需求拆解、参考核对和制作方案文档，提交用户核实确认后，再开始场景、脚本、正式资产、演出与录制实施。** 未确认时可继续读取现有工程、获取参考、抽帧分析和完善文档，不提前把制作方案变成工程修改。用户只要求方案时，交付边界就是文档。

整理方案前必须阅读[需求拆解与制作方案文档](references/production-proposal.md)，按其中规则核对正文、表格、图片和各节独立参考，形成需求逐项对应、实现方法和验收条件。不能只写剧情概要或技术名词；数值/API仅供参考不等于对应效果可省略。

确认应对应可审阅的文档版本，并记录认可范围、条件和未决项。已有明确确认和制作授权则接续执行，不重复索要；用户当前指令明确要求跳过或合并方案阶段时遵从并记录。已确认方案内的局部修复不重走整套审批；影响已确认剧情/结尾或新增制作范围时，先更新相关文档并核实变更。

从用户脚本、参考视频、现有工程和历史确认恢复目标；已有信息足够就行动。先确定会改变制作方案的信息：核心卖点、剧情顺序、必须出现的动作/转折/结局，以及时长、画幅、分辨率、帧率、音频与交付形式。缺少非关键项可采用明确说明的工作假设，不逐项阻塞用户。

在现有项目记录维护简短分镜表：时间或顺序 → 画面动作 → 观众应理解的变化 → 关键角色/道具/UI → 必须保留的结果 → 验收镜头。区分已确认要求、允许窗口和可调表现；具体坐标、人数、时间、资产路径只留在项目中。

**已确认的剧情流程优先于局部优化。** 调路线、密度、动画、镜头、特效或节奏时，仍需保留叙事因果、事件顺序、角色职责及结尾。用户明确修改剧情时更新依据，否则不能以“表现更顺”为由删转折、换结果或改变事件归属。新需求只替代明确冲突的旧要求。

若既定时间与空间运动不兼容，先查路径长度、事件触发、入场安排和镜头表达，完成可独立推进的诊断；确实需要改已确认脚本时，说明具体冲突并请求选择。

## 2. 按镜头选择最合适的实现

先检查现有资产、渲染管线、相机、时间控制和录制条件，复用可用部分。新增素材、工具或包只为解决当前制作需求。

- 关键叙事事件由 Timeline、脚本或既有编排系统稳定控制；需要互动细节时才加入寻路、避让或物理等局部模拟。纯镜头演出可用关键帧/路径，不强制自主 AI、ORCA、NavMesh 或 Rigidbody。
- 编排控制“何时发生、谁承担、结果是什么”；运动与表现实现“怎样连续、可信地发生”。避免多个系统同时改同一位置/状态，明确最终权威来源。
- 保留可复现的时间求值、种子或缓存。需要重播/跳转录制时，验证角色、动画、粒子、UI及结束状态能重建，不让上一次播放残留污染下一次。
- 新场景先用简单资产跑通关键动作与完整剧情，再逐步完善画面；已有成片迭代只改受影响部分，不借机重建无关系统。
- 按需配置易调整的时机、路径、效果和镜头参数，减少散落常量；不为单次镜头建立超出需求的通用框架。

编排允许确定性表演；但同一连续镜头中已展示的动作、目标和反馈要自洽。不能用无关角色抖动、远处受击或未到位就冻结来掩盖状态错误。若用户要求真实交互/占位，就实际实现和验证，不能拿动画或组件存在替代。

## 3. 先让画面可读，再完善表现

以目标画幅的实际相机画面判断。检查主次、视觉重心、前后层次、密度、角色轮廓、背景尺度和 UI/字幕留白；不能只看 Scene 视图或位置数值。让观众看清输入/动作、过程和结果，特效与镜头运动不能遮掉关键变化。

- 动作复杂或静态背景缺少空间信息时，先建立可编辑的可行区域、路径或锚点；相关显示、碰撞和运动约束尽量读取同一数据。不要一遇到问题就继续叠坐标补丁。
- 排列、朝向和环境适配一起检查；整体旋转或缩放不能代替布局设计。运动中的汇入、换位、出场也需成立。
- 动画、特效和声音按参考拆解组成、先后与节奏，区分必须复现的特征和可自由调整项。触发绑定实际对象/事件，角色、武器与反馈使用一致位置。
- 避免同时大改剧情、运动和视觉。保存基线，每批围绕一个因果问题修改，检查对上下游镜头的影响。

**遇到群体移动、通道越界、占位或特殊单位推挤时**，再读[空间与群体演出](references/spatial-staging.md)。用户已指定同类任务的优先方案：地面角色之间的碰撞避让用 ORCA，并补充实际占位/接触保护；静态背景中的桥面先建立可编辑 Mesh 与 MeshCollider，再让运动系统读取同一轮廓。保留这些具体方法，不照搬本片的坐标、人数和剧情；不涉及这些需求的镜头无需引入。

## 4. 按成片目标验证，而非只验证实现

锁定用户指出的对象、时段和画面现象；先追踪实际状态/目标/触发来源，避免修到相邻系统。同一问题再次返工时，读[对应失败案例](references/rework-cases.md)，重审模型和指标，不能继续叠表面动作。

按[验收与录制交付](references/verification.md)执行：

1. 确认本批代码/资源已编译导入并加载；共享编辑器和文件请求按依赖串行，检查结果属于当前版本。
2. 对关键剧情与受影响阶段做直接验证。问每项指标：“用户指出的画面问题仍存在时，它是否也会通过？”
3. 亲自查看实际运行的前后截图与连续片段，覆盖动作进入、持续、退出及状态切换；数值 PASS、生成图片和组件存在都不能代替实际看图。
4. 改全局时间、状态或运动时检查完整播放；局部改动回归受影响镜头和关键结局，不反复扩大无关测试。
5. 交付视频时按目标规格录制并查看实际导出，验证剧情、画幅、节奏、画质与音画同步。只交工程/预览时明确范围，不声称成片已验收。
6. 需要保存场景时，确认已退出播放且状态切换结束，再复位保存；交付包明确版本与依赖。

报告具体改变、最新证据、未完成项与实现边界。工程检查通过、助手看图和用户审美认可分别记录；不能把固定镜头编排描述成完整自主游戏系统。

## 5. 经验沉淀

项目记录保存脚本约束、参数、资产、参考与证据版本。通用案例保留“误判 → 失败修改 → 新增问题 → 根因 → 有效方法 → 防复发检查 → 适用边界”，只抽取能改变后续制作决策的教训，不把某一片的特定剧情和技术路线固化成通用规则。
